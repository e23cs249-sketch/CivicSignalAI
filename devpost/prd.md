# CivicSignal AI — Product Requirements

> Historical planning record: this approved PRD describes the initial plan, which deferred real accounts, map selection, and photo uploads. The dated implementation revision at the end is the source of truth for later shipped behavior; it does not rewrite the original plan or establish learner activity.

AI-assisted civic issue reporting and resolution tracking for everyday public problems, designed as a focused proof of concept for a five-person beginner-friendly team working within hackathon constraints. Source: `scope.md > The Core Loop`, `scope.md > The POC Boundary`, `scope.md > What "Working" Looks Like`, and `scope.md > Explicitly Cut`.

## The Core Journey
1. A citizen opens the app and lands on a simple issue-reporting form.
2. They enter a short description of the problem, choose a category, and optionally add a landmark or location hint.
3. The app performs a clearly labelled rule-based analysis by default to generate a summary, category suggestion, priority hint, missing-detail checks, and duplicate suggestions.
4. If an external free AI service is later attempted, it is only used after verifying availability, usage limits, terms, and any possible charges; it must not be required for the MVP to function.
5. The user reviews the suggested summary, category, missing details, and duplicate suggestions before submitting.
6. The report is saved and visible in both the citizen-facing issue status view and the team dashboard, using the same persisted data layer.
7. A team dashboard displays the submitted issue and allows acknowledgement, status updates, and a resolution note.
8. The citizen sees the status progression and the final resolution message with evidence if provided after the data is reloaded.
9. The report stays visible after refreshes or restarts, demonstrating persistence and continuity using the actual storage solution chosen in `4-spec`.

## Screens and Layout
The MVP should use a small number of lightweight screens, all focused on the core workflow:

### 1. Citizen Reporting Screen
- Header with app name and short explanation
- Description field with placeholder text
- Category selector
- Optional location/landmark field
- AI analysis panel summarizing the issue and identifying missing details
- Duplicate suggestion panel showing possible matches, not confirmed duplicates
- Submit button
- Clear validation feedback when required information is missing

### 2. Citizen Tracking Screen
- List of submitted reports
- Each report shows status, category, summary, and last update time
- Clicking a report opens a detail view
- Detail view includes report status timeline, AI summary, team updates, and resolution note
- Visual distinction between active and resolved status

### 3. Team Dashboard
- List of incoming reports in a queue or table
- Each row shows report summary, category, status, and created time
- Filters for active and resolved reports
- Ability to open a report to acknowledge it, change status, and add a resolution note
- Optional evidence attachment area, but not required for the MVP

### 4. Team Issue Detail Screen
- Report metadata and current status
- Controls to acknowledge the issue
- Status selector with allowed values for the MVP
- Update notes field for team progress
- Resolution note field required to mark the issue resolved
- Optional evidence upload or note field for proof of completion
- Save/update actions with clear confirmation

## Look and Feel
- Clean and approachable, not bureaucratic or intimidating
- Simple, mobile-friendly layout for public reporting
- Professional but friendly interface for team dashboard use
- Strong emphasis on trust and clarity: rule-based outputs must be labelled “Rule-based analysis,” external AI outputs must be labelled “AI-generated,” and heuristic suggestions must not be presented as verified facts
- Use neutral civic-tech colors and readable typography rather than glossy marketing visuals
- Keep everything easy to explain in a short demo video

## Features and Behavior

### Issue Submission and AI Analysis
- A citizen can create a report with a description and category.
- The system uses a clearly labelled rule-based analysis as the reliable default for the MVP.
- An external free AI service may be attempted only after its availability, usage limits, terms, and potential charges are verified.
- The core workflow must remain fully functional without any external AI service.
- Rule-based results must be labelled “Rule-based analysis.”
- Only results actually generated by an external AI service may be labelled “AI-generated.”
- Heuristic suggestions must not be presented as verified facts.
- The system can suggest a summary of the issue in plain language.
- The system can suggest a likely issue category and priority based on report text.
- The system identifies missing required details and highlights them before submission.
- The report is saved immediately after successful submission.

### Duplicate Suggestions
- New report descriptions are compared against existing reports using a simple, explainable method.
- Examples include keyword overlap, normalized text similarity, and category matching.
- The app shows possible duplicates as suggestions rather than confirmed matches.
- Duplicate suggestions are presented in an easy-to-understand panel with a short explanation such as “similar description keywords detected.”
- A user can still submit a report even if a duplicate is suggested.

### Citizen Status Tracking
- A citizen can view a list of their own reports and the current status of each.
- Report statuses update clearly over time as the case moves from submitted to acknowledged to in progress to resolved.
- Status changes must remain visible after page refreshes and app restarts.
- The citizen can open a report detail page to see updates and resolution notes.
- The citizen and team views must read and update the same persisted report records through the chosen backend/data layer and share the same status timeline.
- A status update made in the team dashboard must become visible in the citizen tracking view after the data is reloaded.

### Team Dashboard Actions
- A team member can open a report from the dashboard.
- The team can acknowledge receipt of the report.
- The team can change the report status to reflect current progress.
- The team can add a progress update note.
- A resolution note is required before the issue can be marked as resolved.
- Optional evidence such as a photo or supporting note may be attached or referenced.

### Persistence and Recovery
- Reports and all status updates persist across refreshes and restarts.
- The app should retain the report timeline and current data through the chosen backend/data layer in `4-spec`; SQLite remains a candidate and is not a final decision.
- Persistence after an application restart must be validated using the actual chosen storage solution, not only browser state or temporary in-memory data.
- The app should clearly show when data is local demo data versus real live data.
- The citizen and team views share the same persisted records and status history, without requiring separate, unsynchronized data stores.

## States and Boundaries
- **Empty state** — no reports have been submitted yet; show a friendly empty message and example issue categories.
- **Validation error** — required description or category missing; show inline guidance near the field and disable submission until fixed.
- **AI unavailable/fallback state** — no free AI service available or usage limits reached; show a clear “rule-based analysis mode” label and explain that the output is heuristic.
- **Duplicate warning state** — likely similar reports found; show suggestions without marking them as confirmed duplicates.
- **Acknowledged state** — report received by team and being processed.
- **In progress state** — team is actively updating the issue.
- **Resolved state** — issue marked resolved only after a resolution note is entered.
- **No-result state** — filters or dashboard searches yield no matching reports; show a clear empty-state message.
- **Persistence state** — data survives refreshes and restarts; no silent reset on reload.

## Acceptance Criteria
- **Report submission succeeds** — Given a valid description and category, when the citizen submits the form, then a new report appears in the citizen view and team dashboard with a unique ID, created timestamp, and initial status.
- **Validation blocks incomplete submission** — Given a blank description or missing category, when the citizen attempts to submit, then the form prevents submission and shows a clear inline validation message.
- **Rule-based analysis is the default** — Given no external AI service is available or verified, when the report is created, then the app shows a clearly labelled “Rule-based analysis” panel instead of failing or silently skipping analysis.
- **AI-generated labels are reserved for actual AI output** — Given an external AI service is used and returns a result, when the output is displayed, then it is labelled “AI-generated”; otherwise, no AI label is shown.
- **Heuristic suggestions are not treated as facts** — Given a duplicate suggestion or priority hint is generated from heuristic logic, when the user reads it, then it is presented as a suggestion or probability, not as a confirmed fact.
- **Persistence after refresh** — Given a report has been submitted, when the page is refreshed, then the report remains visible with the same status and history.
- **Persistence after restart** — Given the app is restarted, when it loads, then the saved reports and status timeline are still present and visible to both citizen and team views using the actual storage solution chosen in `4-spec`.
- **Shared data consistency** — Given a status update is made in the team dashboard, when the citizen view reloads its data, then the updated status and timeline are visible in the citizen tracking view.
- **Duplicate suggestions are non-binding** — Given a new description that overlaps with an existing report, when analysis runs, then the system shows possible duplicates as suggestions and does not automatically merge or confirm them; the user can still submit the report.
- **Team acknowledgement updates the shared record** — Given a submitted report, when the team acknowledges it, then the status changes in the shared persisted data and is visible to the citizen view.
- **Progress update is recorded** — Given a report is acknowledged or in progress, when the team adds a note, then the new note appears in the shared report timeline and remains after refresh or restart.
- **Resolution requires a note** — Given a team member attempts to mark a report resolved without entering a resolution note, when they submit the change, then the action is blocked and a clear validation message is shown.
- **Resolution succeeds with note** — Given a resolution note is present, when the team marks the report resolved, then the status changes to resolved and the note remains visible in the citizen timeline.
- **Optional evidence does not block resolution** — Given a resolution note is entered but no photo or additional evidence is provided, when the team resolves the issue, then the report is still marked resolved.
- **No-result state is visible** — Given no existing reports match a filter or search, when the view loads, then a clear empty-state message is shown instead of an empty table or broken panel.

## Product Decisions
- Keep the MVP small and demo-friendly so a five-person team can build it within the hackathon timeline.
- Use simulated notifications and clearly labelled demo data to avoid implying real civic deployment.
- Prefer easy-to-understand, rule-based analysis when free AI usage is unavailable or constrained.
- Keep validation and status transitions explicit so the product is understandable to beginners and easier to test.
- Require a resolution note for resolved status to maintain clear accountability.
- Treat photo evidence as optional for MVP, because it is not required to demonstrate the core workflow.

## What We're Building
The proof of concept must include all of the following:
- a citizen-facing issue reporting flow
- a simple AI or rule-based analysis layer with clear labels
- duplicate suggestions generated from existing report text
- a citizen tracking screen for submitted issues and status updates
- a team dashboard for acknowledgement and updates
- required resolution note to close an issue
- persistence across refreshes and app restarts
- labels that clearly distinguish demo data from real operational data

## Deferred From the POC
- live integrations with government agencies or city systems
- real geospatial mapping or route optimization
- real SMS/email notification systems
- user authentication beyond demo-safe mock flows
- large-scale data processing or analytics
- multi-team routing or department assignment logic
- advanced AI confidence scoring and analytics

## Possible Later Enhancements
- map-based issue visualization and location clustering
- improved duplicate detection using geolocation and historical patterns
- issue assignment across departments or teams
- richer reporting metrics and trend analysis
- better AI summarization and classification quality
- optional photo upload and evidence review on the dashboard

## Non-Goals
- Real-world issue resolution claims or live government integration
- Paid AI service dependency or surprise-charge assumptions
- Large-scale civic deployment or multi-city expansion
- Complex auth, permissions, or role systems beyond the demo MVP
- Production-grade analytics or public reporting dashboards

## Open Questions
None remain; no unresolved question blocks specification approval or implementation.

## Implementation Revision — 2026-10-19

This revision reconciles the requirements with the current application. It documents later implementation and does not imply these features were part of the original approved plan.

### Current user journey
1. A resident registers or signs in. Protected citizen pages redirect anonymous visitors to `/`.
2. The resident enters a report title, supported category, and description, then adds an optional area/address. In the location step, they may select a Leaflet/OpenStreetMap marker or request browser GPS; coordinates must be confirmed before saving. Address-only reports remain possible.
3. The resident may attach up to four JPG, PNG, or WebP photos, each no larger than 5 MB. The review step displays the report before submission.
4. Optional preview returns local rule-based summary/category/priority hints, missing-detail prompts, and possible duplicate suggestions. These are heuristics, not external-AI output or confirmed facts.
5. Submission stores the report, citizen owner, and initial timeline event in SQLite. Optional photos are validated, re-encoded, and stored outside the public static directory.
6. The signed-in citizen sees only their reports and can reopen status, timeline, location, and authorized photos on the tracking page.
7. A staff account provisioned through the interactive utility can sign in to the team dashboard, search/filter reports, review the timeline, add a progress note/photo, and move the status forward or reject with a reason.
8. Staff updates and evidence are saved to the same database. The citizen sees the changes on refresh.

### Current acceptance criteria and boundaries
- Registration/login and protected citizen routes work; report creation and tracking enforce citizen ownership.
- A map location is stored only as a confirmed latitude/longitude pair; manual address entry does not require coordinates.
- Citizen and team images are type/size checked, stored privately, and served only to the owning citizen or authenticated staff.
- Staff updates require authentication and same-origin checks, persist timeline events, and enforce transition rules. Resolution requires a non-empty resolution note; rejection requires a reason.
- SQLite and local filesystem storage persist across restart but are single-host prototype storage. No production city integration, cloud storage, OAuth, password recovery, outbound notifications, or external AI is configured.
- Verification is provided by the existing `pytest` suite, including citizen auth/ownership, API reports, analysis, duplicates, media workflows, persistence, and staff workflow tests. See the implementation revision in `spec.md` and the root README for exact commands.
